# 微信/QQ 读取与发送能力技术研究

研究日期：2026-11-01。用户本轮明确要求这三项只研究，不开发：窗口监听、替代 ExportWeChat、自动发送/主动搭话。本轮未安装第三方工具、未读取聊天数据库、未启动监听、未发送消息。

## 结论与证据等级

QQ 当前会话读取最适合从 UI Automation（UIA）开始；微信完整历史读取需要独立本地数据适配器，OCR 只适合可见内容。不能把“机器人收到的新消息”当作本人微信已有联系人和历史消息的完整读取。自动发送应最后实施，主动搭话也必须经过同一个发送队列。

本报告的仓库信息属于**上游项目自述**；本轮没有在本机微信 4.1.15.56 / QQ NT 9.9.33.52230 上验证兼容性。旧方案的微信 UIA 为空、QQ UIA 可读记录属于既有现场记录，仍需复核。仓库分支会变化，后续技术验证须记录 commit、软件版本、文件哈希和日期。

## 微信读取与替代 ExportWeChat

两种需求应分别验收：A 是读当前会话的新消息；B 是读取指定联系人的既有历史。UIA/OCR 只能覆盖暴露或可见内容，完整历史不能通过一个 OCR 监听器自然获得。Microsoft 的 [UIA 官方说明](https://learn.microsoft.com/en-us/windows/win32/winauto/entry-uiauto-win32) 描述其依赖应用提供的可访问性信息，因此 UIA 为空是数据源限制，不是增加提示词能解决。

建议的技术验证顺序：

1. **无写入 UIA 复核**：只检查目标窗口结构、控件类型和消息节点计数。不要为了让树出现而写微信进程内存。4.1.15.56 若仍不暴露正文，记录失败并停止该路线。
2. **可见 OCR 兜底**：用户选择会话后，只截聊天区域；本机识别消息气泡、左右方向、时间块。低置信结果进入预览，不直接入正式历史。必须覆盖主题、DPI、表情、长消息、引用和连续同文消息；截图默认不保留。
3. **历史数据适配器 Spike**：审阅 wechatauto-replica 的读取模块与权限需求，列清哪些步骤只是打开数据库副本、哪些会访问进程或缓存敏感材料。若选择此路线，独立进程只输出用户选择的会话，不导出整个账号；只读打开一致性快照，绝不修改原始数据库。具体兼容性和数据正确性待实机验证，不在本轮实现。
4. **独立内部格式**：适配器输出统一消息格式，插件不依赖 ExportWeChat 的输出文件。原来的 JSON/HTML 导入器继续兼容旧备份，直到新路径达到验收条件。

本机 ExportWeChat 的已有调查发现其 `ew.exe --help` 涉及初始化凭证及联网会员验证。这个事实不能证明所有互操作性研究都不可做，也不能把它等同于数据库协议本身。REA 后续可用于识别文件格式、组件边界、导出字段和只读调用证据；不绕过会员检查、不重分发其私有代码。独立读取器应从合法获取的文档、开源实现和本人授权数据建立自己的适配层。

REA 准备步骤只应在后续用户恢复该任务后执行：从上游官方包获取 → 检查安装配置变更 → 注册 MCP/选择现有合法分析引擎 → 对程序副本做静态取证 → 输出带位置的证据和局限。其[安装说明](https://github.com/morluto/rea#quick-start)要求设置后重启客户端；因此安装完成不等于当前会话立即有工具。不得把 REA 放进关系手记用户运行依赖。

## QQ 监听建议

优先研究 qq-operations 的只读定位方法，配合 windows2text 复核控件，建立单一会话窗口适配器。第一次只允许用户手工打开目标会话；读取可见范围，来源明确标记为“当前视口”，不宣称完整历史。需要分页时设置屏数上限，滚动前后保存视口位置，并给用户可停止状态。

同一段文本可能是两个真实消息，不能仅按正文去重。优先使用源消息 ID；UIA 无稳定 ID 时，以会话、发送方、时间区块、相邻消息序列和视口重叠做对齐，无法消歧时让用户预览。撤回/编辑必须作为独立修订事件，不覆盖错误联系人。后台/最小化失去树时报告暂停，不静默返回“没有新消息”。

## 后续桥接契约（设计建议，未实现）

本机 helper → 带随机令牌的本机宿主通道 → 有界队列/read/ack → 关系手记导入。桥接只监听 loopback 或采用继承管道，避免开放无鉴权网络端口。推荐每条事件包括：

```ts
type CaptureEvent = {
  source: 'wechat' | 'qq'; accountKey: string;
  conversationKey: string; sourceMessageId?: string;
  senderKey: string; direction: 'self' | 'target' | 'unknown';
  text: string; timestamp?: string;
  observedAt: string; dedupeKey: string;
  scope: 'visible' | 'history'; confidence: number;
  revisionOf?: string;
};
```

`accountKey`、会话映射只存本机；标题/备注名不能作为唯一联系人键。首次出现进入待绑定列表，用户确认后再合并，禁止自动按同名归并。读取时间与原消息时间分开存储；无时间时留空，不能伪造当前时间为发送时间。

## 自动回复与主动搭话的可执行方案

此项本轮仅研究。后续先实现“生成草稿 → 用户确认 → 填入指定会话”，通过后才研究发送。主动搭话的调度器只生成候选意图，不直接触碰发送 API；用户的本人档案决定表达风格，联系人档案提供事实背景。

采用统一状态机：`proposed → approved → queued → recipientChecked → dispatched → confirmed / uncertain / failed / cancelled`。发送结果不明时进入 `uncertain` 并停止重试，防止重复消息。所有入口共用收件人核对、内容/会话幂等键、单会话冷却、静默时段、每日额度、全局停止和会话白名单。出站内容在最后一步与用户看到的预览一致；会话切换立即撤销许可。日志只记事件 ID、结果和时间，不记正文。

主动话题候选可来自明确待跟进事项、双方已确认兴趣、用户自己的近期计划。不可把在线状态、沉默或模型猜测当作“必须主动联系”的触发条件。若未来启用自动发送，应以明确开启的会话及有限时段为授权范围，每轮可跳过，不为了凑额度发送。

## 后续恢复实施时的最小验收矩阵

| 维度 | 必测条件 | 通过条件 |
|---|---|---|
| 窗口 | 前台、后台、最小化、锁屏、切会话、多账号 | 状态准确；不串账号和联系人；不可读时暂停。 |
| 消息 | 同文重复、乱序、跨日、引用、撤回/编辑、附件、群聊 | 不丢原始方向和时间；未知不猜；与人工样本逐条对照。 |
| 增量 | 初次读取、重叠视口、重启、队列满、ack 失败 | 不重复入库；未确认记录可恢复；不无限积压。 |
| 发送 | 切错窗口、重复请求、断网、未知回执、用户停止 | 错会话拦截；不重复发送；未知结果不盲重试；停止及时。 |
| 发布 | 依赖许可、二进制来源、敏感日志、账号数据 | 固定版本及哈希；保留许可证；发布包不含个人资料。 |

每个适配器先用用户自建测试会话构造样本，再测有限真实会话。稳定运行统计必须标明样本量和时长；上游的测试数量不能替代本机验收。建议产物为版本适配表、失败场景列表、样本比对报告和是否继续的决策记录，再进入代码实现。
