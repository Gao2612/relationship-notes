# 自动分析与兴趣依据审查

日期：2026-11-01。本文记录本轮独立审查；自动调度与服务仍由其他智能体实现，不能据此宣称已完成整链验收。

## 兴趣建议的真实缺陷

`engine.supportedProfileSummary` 只检查引文包含喜欢/不爱/不喜欢/感兴趣等词。此检查能排除部分“只参加过一次”活动，却不能验证value与quote一致；否定偏好也会通过。host的profile-analysis另外只校验quote是消息连续子串，同样不证明摘要里的“喜欢农场”来自这条引文。

负向偏好本身是应当保存的资料，不能为修复建议而删除全部含否定的档案。问题出在建议把混合摘要当作一个正向兴趣，并配上其中一条否定引文。

新增 `src/preference-evidence.js` 提供保守局部分句分析：`extractPreferenceEvidence` 返回positive/negative/ambiguous，`selectPositivePreference`只从原文quote提取明确正向对象及其原句，`hasNegativePreference`用于识别刚明确否定的话题。它不是通用语义蕴涵模型，无法识别的表达宁可不自动作为正向兴趣。

已覆盖截图反例：混合value“喜欢农场游戏，但不喜欢其他游戏及麻将”，引文“没有没有，我本来对游戏啊、麻将啥的都不感兴趣”时，没有正向候选。引文“我不爱其他游戏，但喜欢玩农场”能保留农场，并排除其他游戏；转折不应导致整条消息被一刀否定。双重否定、提问、第三方引语、以前的偏好和一次活动不会自动进入正向候选。

建议宿主提取提示要求一条事实仅表达一项可由其引文支持的主张，混合正/负偏好应拆开；返回值校验仍无法完全证明语义一致，新模型资料必须维持pending确认。用户手动确认的摘要也不能替代逐条依据；自动话题应优先使用局部正向原文，或请用户核对缺失来源。

## 自动全量/增量分析的集成检查要求

- 初次有序分批遍历全部有效消息，之后只处理新增或变更的片段。当前history接口每批最多20条、每条2000字符，摘要最多4000字符；长消息截断情况应可见，不能承诺理解了未发送的文本。
- 检查点至少记录有序稳定消息ID及内容摘要、累计memory、已完成位置、模型和分析协议版本。只按条数或最后ID判断会漏掉旧消息编辑、排序和删除。
- 每批成功立即保存，刷新可恢复，不从头重复计费。选择不同联系人或取消后旧结果不得写回；共享授权不能因自动分析缓存恢复而开启。
- 模型/本人语气变化应重算最终解释，尽量复用与表达风格无关的全历史摘要；消息内容或双方身份变化则需要从受影响批次重算历史。
- 对同一联系人/签名单飞；失败进入明确暂停或有限重试，不通过每次render/useEffect重复请求。多窗口同时分析的重复费用风险应明确处理。
- 显示已完成批数/剩余批数、当前模型和停止入口。模型失败、截断、非法JSON及伪造引用均不能标记成已完成缓存。

## 需要的真实行为集成用例

1. 45条虚构消息首次自动调度：3次history分批调用后1次解释；不靠人工点击启动。重渲染及读取持久缓存后零额外调用。
2. 增加1条消息只增加一个增量批次和一次最终解释；改动早期消息会使旧检查点失效，不能复用错误摘要。
3. 第2批模拟超时：只保存第1批成功检查点，停止重复渲染扣费，恢复时从第2批继续；取消信号传递到真实handler的prepared.stream。
4. 并发切联系人A→B，A延迟结果返回后不污染B，回到A仅读取匹配签名的缓存。
5. provider/model及本人语气变化分别验证缓存失效范围；请求中历史摘要只能作背景，原文引用必须仍指向此次messages中的真实ID。
6. 真正调用模型handler的mock LLM（而非只比较源码字符串）：覆盖text-delta、block-end、重复块、length结束、异常、非法JSON、伪造quote，确认没有成功缓存坏结果。

上述场景应在自动调度模块落地后运行，不能用“测试里手工拼分批数组”代替实际调度行为。
